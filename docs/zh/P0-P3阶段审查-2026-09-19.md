## R4 / P1：任务说明等资源元数据更新会永久阻止兼容实例运行

定位：`MFAAvalonia/Configuration/Compatibility/ProfileSnapshots.cs:44`，尤其递归比较的第 50～57 行；调用位置 `MFAAvalonia/Extensions/MaaFW/MaaProcessor.cs:2746`。上游资源同步位置 `MFAAvalonia/Extensions/MaaFW/TaskLoader.cs:444`。

`VerifyLoadedTasks()` 对保存的 `TaskItems` 整个 JSON 做递归值保留校验，包含 `description`、label、pipeline override 等资源定义字段。上游 `UpdateExistingItem()` 会按新 interface 正常更新这些字段。只要新资源改变任务说明，现有校验就会认为用户配置丢失；`InitializeData()` 随后恢复旧配置、冻结写入，并将实例加入 `FailedTransitions`。

所有迁移/完整导入实例都会带 `Compatibility.Isolated`，该检查并非一次性。原数据恢复后下次启动仍遇到同一新资源，形成持续失败，不能通过提示重启解决。

最小输入：保存任务的 `name/entry/check/option` 不变，仅把加载结果中的 `description` 从 `old help text` 改为 `new help text`。

实际结果：

```text
R4 metadata-only update rejected: 当前资源重载会改变备份中的 TaskItems，已停止应用并保留原配置。
```

修复要求：明确区分用户保存的选择/输入/顺序与资源作者维护的元数据，按稳定任务与选项身份验证用户状态保留。合法资源元数据更新应通过；任务/选项删除或不兼容值应保留原数据并形成明确报告，不能简单移除全部保护。

补测：真实 TaskLoader 路径中的说明/标签更新、资源任务重命名兼容、合法选项定义演进；同时验证任务勾选、顺序、重复次数、输入值或独立 Copilot 状态确实丢失时仍能发现。

## R1 / P1：非当前配置中的启用定时被迁移为立即生效的全局规则

定位：`MFAAvalonia/Configuration/Compatibility/LegacyConfigurationReader.cs:207`、`:254`；执行筛选为 `MFAAvalonia/ViewModels/Other/TimerModel.cs` 的 `CheckCompatibilityTimersAsync()`。旧行为可核对 fork `TimerModel.ReloadFromConfig()` 和配置切换后的调用。

迁移器对每个配置快照都执行 `ConvertTimers()`，并把原启用状态原样写成全局规则。规则只保留源文件字符串 `.Source`，没有用于调度的来源配置身份/生效条件；运行筛选也不检查来源配置是否激活。

旧 fork 每实例的 TimerModel 从该实例当前绑定配置读取，切换配置后重新加载，所以未激活配置的已启用规则只是保存状态，不会同时执行。保存全部规则与让全部规则同时生效是不同要求。

最小输入：实例 `a` 绑定 `Default`，当前任务为 A；`Default` 有 10:00 定时。另一个 `mfa_Night.json` 保存任务 B、11:00 的启用定时、`CustomConfig=False`。

实际迁移结果：

```text
R1 inactive Night rule: enabled=True, scope=Instance, targetProfile='', activeTask=A
```

因此该来源于 Night 的规则会进入全局调度，11:00 不切配置而执行当前的 A。不同配置恰有相同时刻的规则还可能被错误认定为并发冲突。

修复要求：独立保存规则的来源配置与目标配置，并保留旧配置激活条件及启用状态；不要通过永久禁用/删除非当前配置规则来丢弃行为。两分钟前发生配置切换后，本次已预约触发与后续配置规则的交接须有明确状态语义，防止切换导致本次预约被取消或重复执行。

补测：Default/Night 都保存启用规则但仅当前配置生效；A→B→A 后对应规则集正确；非当前配置规则在同/不同时刻均不误跑；预切换后本次发生仍按预期完成。

## R2 / P1：无配置切换的强制定时提前两分钟停止当前任务

定位：`MFAAvalonia/Configuration/Compatibility/CompatibilityScheduler.cs:73`；上层会传入未来两分钟的全部兼容开始规则。

调度器在整个预切换窗口里，只要实例忙碌且 `Force=true` 就调用 `RequestStopAsync()`，没有区分“确实要切换配置”与“仅到时强制重启”。旧 `TryPreSwitch()` 在 `CustomConfig=false`，或目标已经是当前配置时直接返回；这些规则只在正式触发时才停止任务。

最小输入：`ProfileId=""`、`Force=true`、实例忙碌，规则发生时间 T；在 T−2 分钟评估。

实际结果：

```text
R2 non-switching forced rule at T-2: StopRequests=1; old behavior requires 0 until T.
```

修复要求：将预切换准备与到时强制启动分开。只有确有切换需求的规则才按旧策略提前请求停止；无切换或目标已激活时保持当前任务直到 T，并继续等待真实释放后启动。

补测：CustomConfig=false + Force=true；目标已经激活 + Force=true；确实跨配置 + Force=true；Force=false。逐项断言停止请求的时点，不能只断言最终停止过一次。

## R3 / P1：较晚规则提前占用实例，导致较早规则被判冲突而跳过

定位：`MFAAvalonia/Configuration/Compatibility/CompatibilityScheduler.cs:40`、`:53`、`:64`。

规则按 RuleId 排序，而预约以实例为键并从预切换一直持有到发生分钟过后。同一实例的多个不同发生时间同时落入两分钟窗口时，如果较晚规则的 RuleId 排序靠前，它会先取得预约，较早规则到点被认定为冲突并写入 `_attempted`，不会再执行。迁移 RuleId 来自 hash，不能表达时间先后。

最小输入：同一实例，两条不切换配置的规则分别为 `01-later`（10:02）和 `02-earlier`（10:01）；10:00 进行预处理，10:01 再评估。

实际结果：

```text
R3 adjacent occurrences: startsAtEarlierTime=0, reports=02-earlier:同一实例的定时冲突，本次未执行。; expected earlier rule to start.
```

修复要求：预约按实际发生时间协调，同一发生时间才使用稳定身份确定顺序；处理更早规则加入/修改后的预约失效与重排。不要让未来规则阻止当前到期规则，也不要仅交换排序后忽略已有预约。

补测：同实例相隔 1～2 分钟且 RuleId 逆序；预约后插入/修改更早规则；真正相同发生时间冲突；多个实例同一分钟仍独立执行。
