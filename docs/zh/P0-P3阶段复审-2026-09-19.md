## 2. R5 / 优先级 P2：迁移定时改绑实例后，来源身份仍指向旧实例

定位（均相对集成工作树）：

- `MFAAvalonia/ViewModels/Other/TimerModel.cs:450`：SourceProfileId 只读，激活检查使用当前 TimerConfig 对应实例的活动配置。
- `MFAAvalonia/ViewModels/Other/TimerModel.cs:589`：TimerConfig setter 只保存新实例并刷新列表，未处理来源和目标快照引用。
- `MFAAvalonia/Views/UserControls/Settings/TimerSettingsUserControl.axaml`：界面允许修改所属实例，但来源配置只有说明文本，没有修复或重新选择入口。

复现使用实际 `TimerModel.TimerProperties`、`InstanceConfiguration` 和 `CompatibilityTimerRuntime`，不调用设备：

1. 实例 A、B 各有一个活动 Default 快照，ID 分别为 `review-a-default`、`review-b-default`。迁移器实际也按实例 ID + 来源文件生成不同快照 ID。
2. 一条已启用迁移规则属于 A，SourceProfileId 指向 A 的 Default，目标选择“当前配置（不切换）”。此时来源激活检查为 true。
3. 通过界面绑定的 TimerConfig setter 改为 B，仍选择“当前配置（不切换）”。
4. 来源身份仍是 `review-a-default`；调度器在 B 中找不到这个活动身份，永远不准入。重建 TimerProperties 后同样失效。

实际输出：

```text
OBSERVED before edit: sourceActive=True, source=review-a-default, instance=review-a
OBSERVED after edit: sourceActive=False, source=review-a-default, instance=review-b, target='', admitted=False
OBSERVED after reload: sourceActive=False, source=review-a-default, label=来源配置：缺失（仅激活时生效）
```

影响：用户正常修改已迁移规则的所属实例后，规则仍显示启用却不会再执行。即使目标选回当前配置、反复开关定时或重启也无法修复；现有界面不能修改来源，只能改回旧实例或删除重建。该问题由新增来源激活约束与已有编辑入口之间的不一致引起。

修复要求：为“更改规则所属实例”实现完整的引用更新语义。实例、来源快照、目标快照应一起校验和持久化；有唯一可靠映射时可重绑定，否则提供明确的来源/目标选择或拒绝保存不完整变更。**不能直接清空 SourceProfileId，把原本有激活条件的规则变成始终生效。** 已有固定规则的 RuleId、时间、重复计划、Force 和启用状态应保留。

建议补测：真实 TimerProperties 从 A 改到 B，两个实例快照 ID 不同，包含“当前配置”和指定目标两种情况；验证来源/目标有效、发生能够准入、保存重载一致。目标实例缺少相应快照时，应有可在界面完成的处理方式，不能留下无法编辑来源的失效启用规则。

## 3. R6 / 优先级 P2：单选变成输入或多选后，旧选择被保留在 JSON 中但不再生效

定位：

- `MFAAvalonia/Extensions/MaaFW/TaskLoader.cs:154`：只在新定义仍是 select/switch 时检查 index 范围；当新类型为 input/checkbox 时，旧 index 没有兼容性检查。
- `MFAAvalonia/Configuration/Compatibility/UserTaskState.cs`：只比较保存前后的 index 数值，因此旧 index 仍在 JSON 中就通过。
- `MFAAvalonia/Extensions/MaaFW/MaaProcessor.cs:3774`、`:3823`：运行参数按新类型读取 SelectedCases 或 Data；这些分支不使用旧 select 的 Index。

复现使用实际 TaskQueueViewModel 和 TaskLoader.LoadTasks，与正式资源加载测试采用同一生产路径：

1. 保存一个任务，选项 `mode` 的旧选择为 `index=1`，即旧 select 的第二个 case。
2. 新资源仍保留同名任务、同名选项，把 mode 改为 input 并提供默认输入 `new-default`；另一组改为具有同样 case 名称的 checkbox。
3. 两组加载均成功并持久化，兼容校验没有拒绝。

实际输出：

```text
OBSERVED select -> input accepted: [{"name":"mode","index":1,"data":{"value":"new-default"}}]
OBSERVED select -> checkbox accepted: [{"name":"mode","index":1,"selected_cases":[]}]
```

影响：JSON 的 `index=1` 虽然没有丢，后续 input 使用新默认输入，checkbox 使用空选择；旧选择的有效行为已被静默替代。新增的类型检查目前覆盖“已有多选变成非多选”“已有输入变成非输入”等方向，却没有覆盖原单选的方向。这与只缺少旧 case 名称、无法推断 case 重排的已知限制不同：这里可以从已保存的非空 index 与新类型不匹配发现问题。

修复要求：校验已保存状态能否被新类型实际使用，而不只核对 JSON 值相等。对旧 select/switch 到 input/hotkey/checkbox 等变化，有可靠依据时显式转换并验证有效结果；没有依据时恢复原数据并给出清楚的兼容性错误。应考虑历史数据中残留字段的情况，不以一刀切类型判断误伤正常 input/checkbox 加载，也不要通过删除 index 检查或统一采用新默认值规避。

建议补测：实际 TaskLoader 路径下 select/switch → input、checkbox 的不兼容加载，验证拒绝或明确转换、内存及磁盘状态、重复重载结果；原有元数据更新、选项按名称重排、新字段默认值追加仍应通过。
