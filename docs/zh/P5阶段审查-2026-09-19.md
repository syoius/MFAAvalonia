## P5-R1 / P1：普通连接失败会永久冻结录制实例及共享资源

触发：用户点击开始录制，资源已加载、Tasker 已创建，但控制器连接失败。例如所选设备掉线或连接失败。这里不是录制动作已经运行而无法停止的情况。

调用链：

1. `MFAAvalonia/Extensions/MaaFW/MaaProcessor.cs:1907` 等待 `LinkStart()`。失败分支在录制期间不直接销毁 Tasker，随后 `:2028` 的 finally 将这个未完成初始化的 Tasker 交给 `MaaProcessor.MaaTasker`，等待会话清理。
2. `MFAAvalonia/Helper/RecordingSession.cs:214` 无条件调用 `tasker.Stop().Wait()` 并要求成功。当前 MaaFramework 对尚未初始化的 Tasker 返回失败，日志为 `Tasker not inited`、`runner id not found [task_id=0]`。
3. 因此本来应该处理未初始化对象的 `:216` 清理分支没有机会执行；catch 在 `:230`、`:231` 把实例和实际资源路径都标记为直到重启才解除的阻塞，并保留会话租约。
4. `_stop` 缓存了这次结果，后续结束/放弃仍不能完成；正常任务及共享路径的其他实例也无法重新取得相关资格。界面提示重启，但主窗口的录制退出拦截也依赖 `RequestEndAsync()` 返回 true（`Views/Windows/RootView.axaml.cs:256`、`:277`），正常关闭路径同样不能收敛。

独立复现使用有效本地 pipeline、生产 `StartRecordingCommand`、真实 `MaaCustomController` / `MaaTasker` 及 native `LinkStart` / `Stop`；仅用自定义控制器替代设备，让连接明确失败。没有替换 `RecordingDeviceEffects.Initialize/Stop`，也没有提交录制动作。观察结果：

```text
OBSERVED failed native connect cleanup:
recording=True; endAccepted=False; released=False;
resourceWriteAllowed=False; retryAllowed=False
```

这不是“真实设备尚未验收”造成的不确定性，而是现有 binding 对未初始化 Tasker 的实际返回值与清理代码不匹配。

修复范围：区分“连接 job 已结束、Tasker 尚未成功初始化、没有录制动作”的可清理失败，与“已提交操作仍未能安全停止”。核实并清理初始化过程中产生的控制器、资源及 Agent，安全完成后释放会话并允许重试；不要简单忽略所有 Stop 失败，也不要取消真正无法停止时的资源保护。新增回归应经过原生未初始化 Tasker 的生产清理路径，证明连接失败后结束和重试可用，且真正的停止失败仍保持保护。

## P5-R2 / P2：原生连接等待阻塞界面，无法及时响应停止或关闭

触发：从录制页面开始录制，需要初始化控制器，连接有延迟。离线或连接缓慢的设备属于正常支持路径。

`RecordTaskViewModel.StartRecordingAsync()` 在 UI 线程调用 `RecordingSession.InitializeAsync()`。`RecordingSession.cs:120` 进入 `MaaProcessor.GetRecordingTaskerAsync()`（`:1069`）及 `InitializeMaaTasker()`；前面几个异步操作之后仍恢复到 UI 上下文。`MaaProcessor.cs:1907` 直接调用 `tasker.Controller.LinkStart().Wait()`，同步阻塞该线程。

因此即使会话提供取消方法，用户的停止、关闭和其他界面输入也无法在这段连接等待中得到处理。现有正式测试替换了整个初始化效果，不能覆盖这个生产内部的同步等待。

同一隔离复现安装正常 Avalonia UI 同步上下文，在真实 native Connect 回调内向 UI 投递一个操作，并等待最多 800ms 后返回连接失败；主线程按正常 headless 方式处理 Dispatcher。结果：

```text
OBSERVED native recording initialization:
connects=1; UI_callback_ran_during_connect=False
```

800ms 是复现的有限等待，避免审查程序挂住；问题来自确定的 UI 同步等待调用链，不要求毫秒级竞争。该回调直到 native Connect 返回后才有机会执行。

修复范围：把录制初始化路径中的阻塞原生等待移出 UI 线程，正确保留 UI 更新的线程归属，并让停止请求在连接期间可以被处理。取消外层等待仍不能当成原生工作已经结束；实际 job 和初始化清理完成前应继续持有占用。补一条能进入生产原生连接等待的界面响应/取消回归，无需重写执行引擎或引入新的平台框架。
